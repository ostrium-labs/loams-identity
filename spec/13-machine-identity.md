# 13. Machine identity `[P3]`

This file covers principals that are not people: service accounts and agents. It specifies how
they authenticate (private-key JWT, client secrets, personal access tokens), the device
authorization grant for command-line tools, and token exchange for agent delegation, workload
identity federation and token attenuation.

Everything here is Phase 3 unless marked otherwise. The feature switches are in
[03](03-data-model.md) section 3 (`client_credentials`, `device_flow`, `token_exchange`, `pats`).

## 1. Principals

A machine user ([03](03-data-model.md) section 2.3) has `kind: machine` and a `purpose`:

| Purpose | What it is | Loams principal kind | May hold |
|---|---|---|---|
| `service_account` | A non-human workload that is not an agent: a batch job, a CI pipeline, a backend | `service_account` | Machine keys, client secrets, PATs |
| `agent` | An AI agent: a coding agent, an assistant, an MCP client acting for itself | `agent` | Machine keys, trust policies. No client secrets by default, never PATs |

**MACH-1.** Every access token issued to a machine principal carries `principal` set to
`service_account` or `agent` ([15](15-loams-integration.md) section 2). An agent's tokens also
carry `agent_owner`.

**MACH-2.** An agent can receive tokens only while it is `active` and has an active owner
(DM-8). Every token-issuing batch read-checks the agent's user stream and, when present, the
owner's (ES-10).

### 1.1 A machine user is its own client

**MACH-3.** A machine user is addressed as an OAuth client by a client id equal to its user id
in canonical lower-case hyphenated UUID form. Its credentials (machine keys, client secrets) are
the client's credentials. No separate application record is needed for a machine principal to
use the token endpoint.

**MACH-4.** Application client ids chosen by an admin MUST NOT parse as a UUID, so a machine
user's client id can never collide with an application's. The `client_ids` index
([05](05-event-store-and-projections.md) section 4) holds both kinds; a machine user's entry
points to the user.

**MACH-5.** A machine user's implicit client is a client of kind `service`
([07](07-oauth-core.md) section 2): confidential, with the grant types `client_credentials`,
`urn:ietf:params:oauth:grant-type:jwt-bearer` and
`urn:ietf:params:oauth:grant-type:token-exchange`. It never uses the authorization endpoint, the
device flow or refresh tokens.

**MACH-5a.** *Conservative choice:* the `service` kind exists only as the implicit client of a
machine user. An admin cannot create a standalone `service` application, because every token
must name a principal that Loams knows (`user`, `service_account` or `agent`), and a client on
its own is none of these.

## 2. Machine keys

**MACH-6.** A machine key is a public key registered on a machine user
(`user.machine_key_added`). The private key is generated by the client and never sent to the
server. *Conservative choice:* the server does not generate key pairs for clients, because a
server-generated private key has to be delivered once and could be logged or cached on the way.
An admin tool in the `cli` may generate a key pair locally and register only the public half.

**MACH-7.** Accepted key types and algorithms, matching the client-assertion profile of KEY-17:
Ed25519 (`EdDSA`), P-256 (`ES256`), P-384 (`ES384`) and RSA of 2048 bits or more (`RS256`,
`PS256`). Keys with private members are refused (as in [06](06-keys-and-jose.md) section 8), and
a key whose JWK thumbprint ([RFC 7638]) equals an existing key of the user is refused. Every machine key has an `expires_at` no more than 1 year
after creation; the default is 90 days. A user may have at most 10 active keys.

**MACH-8.** The key id is assigned by the server (random, 16 bytes, base64url) and returned on
registration. The client puts it in the JWS `kid` header. For machine users `kid` is required,
which is stricter than KEY-17 step 6 (that step allows a missing `kid` when one key matches): the
server assigned the ids, so a client always knows them. A `kid` that names no active key of the
asserted user fails authentication; the server never falls back to trying other keys.

## 3. Client authentication with a JWT assertion (`private_key_jwt`)

Used by machine users and by confidential applications registered with
`token_endpoint_auth_method: private_key_jwt` ([RFC 7523] section 2.2 and 3, [OIDC Core]
section 9).

The request carries `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`
and `client_assertion=<JWT>`.

**MACH-9.** The assertion is validated as a "client assertion" per KEY-17 (header, `alg`,
forbidden header members, `typ`, key selection, signature, time claims with the 60-second skew
of KEY-18) and OAUTH-28 (`iss` and `sub` equal the client id; `exp` at most 5 minutes after
`iat`; `jti` required and recorded in the replay cache). This file adds only:

1. The key set is the machine user's active, unexpired machine keys (section 2), or for an
   application, its registered `jwks` or `jwks_uri` set ([06](06-keys-and-jose.md) section 8).
2. `aud` is the instance issuer identifier as its only value (KEY-19). *Conservative choice,
   with an interoperability cost:* client libraries that still send the token endpoint URL, as
   [OIDC Core] section 9 used to suggest, fail with `invalid_client`. The current revision of
   [RFC 7523bis] makes the issuer the sole audience to close an audience-injection attack, and
   we follow it rather than loosen it. The error is logged with the reason "audience is not the
   issuer" so operators can tell clients what to fix.
3. The replay-cache entry for `jti` is keyed `(instance, client id, jti)` and expires at
   `exp + 60s`, through `MetaStore::put_if_absent` (ES-8 decides expiry by `Clock`).

Any failure gives `invalid_client` with HTTP 401 (OAUTH-29) and an
`observed.client_auth_failed` observation.

**MACH-10.** For an application with a `jwks_uri`, fetching and caching follow
[06](06-keys-and-jose.md) section 8 and KEY-17 step 7. The URL must also pass the outbound URL
rules in [15](15-loams-integration.md) section 5.3.

**MACH-11.** The same assertion rules apply at every endpoint that authenticates clients: token,
introspection, revocation, PAR and device authorization.

## 4. JWT bearer grant

A machine user exchanges a self-signed assertion for an access token ([RFC 7523] section 2.1).

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion=<JWT signed with a machine key>
&scope=<optional>
&resource=<optional, RFC 8707>
```

**MACH-12.** The assertion is validated per the "JWT bearer grant" profile of KEY-17 (`typ`
absent or `JWT`), against the machine user's active keys, with the lifetime and `jti` rules of
MACH-9, and with two differences:

- `iss` and `sub` are the machine user's id (the client is the user itself, MACH-3).
- `aud` may be the issuer identifier or the token endpoint URL, as a single value. The current
  revision of [RFC 7523bis] allows either for authorization grants.

**MACH-13.** No separate client authentication is required for this grant, because the assertion
already proves possession of the machine key. If the request also carries client
authentication, it must identify the same machine user, or the request fails with
`invalid_grant`.

**MACH-14.** The response contains an access token only. No refresh token is issued
([RFC 7523] section 2.1 leaves this open; we choose none, so a stolen refresh token cannot
outlive a revoked key).

## 5. Client credentials grant

[RFC 6749] section 4.4, for machine users that authenticate with a client secret or
`private_key_jwt`.

**MACH-15.** The grant is available when the instance feature `client_credentials` is on and the
client is a machine user (MACH-5). Applications other than machine users cannot use it.

**MACH-16.** Client secrets are generated by the server (32 random bytes, base64url, prefixed
`lics_`), shown once in the creation response, and stored as SHA-256 (DM-4). A machine user may
have at most two secrets at a time, so a secret can be rotated without downtime. Each secret has
an `expires_at`, at most 1 year after creation, default 90 days.

**MACH-17.** Accepted client authentication methods: `client_secret_basic`, `client_secret_post`
and `private_key_jwt`. Secrets are compared in constant time against every unexpired secret of
the user, and the comparison loop always runs over both slots, so timing does not reveal which
slot matched.

**MACH-18.** *Conservative choice:* an agent cannot hold client secrets unless the org setting
`allow_agent_client_secrets` is on (default off). Agents outside a sandbox use machine keys;
agents inside a sandbox never hold a long-lived credential at all (Loams design 76 section 10).

**MACH-19.** The response contains an access token only, never a refresh token
([RFC 6749] section 4.4.3). The token's `sub` is the machine user's id and its lifetime is the
token policy's `access_token_ttl`, capped for agents by `token_ttl_cap` (section 7.5).

## 6. Personal access tokens (PATs)

A PAT is a long-lived opaque bearer token for a service account that cannot use the flows above.

**MACH-20.** PATs are off by default (instance feature `pats`). When on, only machine users with
purpose `service_account` can have them. *Conservative choice:* agents never get PATs; Loams
design 76 section 10 decides that agents use short-lived tokens only.

**MACH-21.** A PAT is `lip_` followed by base64url of 32 random bytes. It is shown once, stored
as SHA-256 in the `pat_hashes` index, and carries a fixed set of scopes and an audience chosen at
creation. `expires_at` is required, at most 90 days after creation by default; an instance
setting may raise the maximum to 365 days, never further.

**MACH-22.** A PAT is opaque. Resource servers validate it by introspection
([08](08-tokens.md)). Introspection of a PAT returns `active: true` only if the PAT is unexpired
and not revoked, and the user, org and instance are active. The response has `token_type: "pat"`
(our value) and the same `principal` and `org` fields as an access token.

**MACH-23.** A PAT is not accepted at the token endpoint as a grant or as client
authentication. *Conservative choice:* it cannot be exchanged for other tokens, so a leaked PAT
cannot be widened.

**MACH-24.** `last_used_at` is updated at most once per hour per PAT, so a busy PAT does not write
an event per request.

## 7. Token exchange

[RFC 8693]. One grant serves three uses:

| Use | Subject token | Actor | Result `sub` | Result `act` |
|---|---|---|---|---|
| Delegation: an agent acts for a user | The user's access token | The authenticated agent client | The user | The agent, with any earlier chain nested |
| Attenuation (vending): narrow a token for a sandbox | An access token of this issuer | None | Same as the subject token | Same as the subject token |
| Workload identity federation: an agent proves itself with its runtime's token | An external JWT | None | The agent | None |

**MACH-25.** The grant is available when the instance feature `token_exchange` is on and the
calling client has the token-exchange grant type.

### 7.1 Request

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:token-exchange
&subject_token=<token>
&subject_token_type=urn:ietf:params:oauth:token-type:access_token
&actor_token=<optional>
&actor_token_type=<required if actor_token is present>
&requested_token_type=urn:ietf:params:oauth:token-type:access_token
&scope=<optional>
&resource=<optional, repeatable>
&audience=<optional, repeatable>
&agent_session=<optional, our extension>
```

**MACH-26.** Accepted `subject_token_type` values:

| Value | Accepted for |
|---|---|
| `urn:ietf:params:oauth:token-type:access_token` | Delegation and attenuation; the token must be a JWT access token or opaque access token issued by this instance and currently active (checked as introspection would) |
| `urn:ietf:params:oauth:token-type:jwt` | Workload identity federation only |
| `urn:ietf:params:oauth:token-type:id_token` | Workload identity federation only, when the trust policy's issuer is an OIDC provider |

Refresh tokens, PATs and ID tokens of this instance are refused as subject tokens with
`invalid_request`. *Conservative choice:* an ID token is for the client that received it, not a
credential to be exchanged ([OIDC Core] section 2).

**MACH-27.** `requested_token_type` may be omitted or be
`urn:ietf:params:oauth:token-type:access_token`. Any other value fails with `invalid_request`.
The response's `issued_token_type` is always
`urn:ietf:params:oauth:token-type:access_token`. No refresh token is ever returned from token
exchange.

**MACH-28.** `actor_token`, when present, must be an access token of this instance whose `sub`
is the same principal as the authenticated client. A mismatch fails with `invalid_request`. The
actor is always the authenticated client; `actor_token` only lets a caller prove it explicitly.

### 7.2 Narrowing rules (all uses)

**MACH-29.** The issued token never has more than its inputs:

- `scope` is a subset of the subject token's scopes. Omitted means the same scopes. Requesting a
  scope the subject token does not have fails with `invalid_scope`.
- The audience (from `resource` per [RFC 8707] and `audience` per [RFC 8693] section 2.1, both
  matched against registered resource identifiers of `resource_server` applications in the same
  org) is a subset of the subject token's audience. Omitted means the same audience. An unknown
  or wider value fails with `invalid_target`.
- `exp` is at most the subject token's `exp`, and at most the limits in section 7.5.
- `auth_time`, `acr` and `amr` are copied from the subject token, never raised.
- `org` is copied from the subject token. A token exchange never changes org.

### 7.3 Delegation

**MACH-30.** The client must be an agent (a machine user with purpose `agent`) in the same org as
the subject token's `sub`, authenticated with `private_key_jwt` or, inside a Loams sandbox, a
token from section 7.4. The subject token's `sub` must be a human user.

**MACH-31.** Delegation is allowed only when one of these holds, checked in this order:

1. The subject token carries a `may_act` claim ([RFC 8693] section 4.4) whose `sub` is the agent.
   This server puts `may_act` into a user's access token when the user consented, at the
   authorization endpoint, to the agent acting for them (the client is an agent-bound
   application, section 7.6).
2. The user has an active grant to an application bound to this agent (section 7.6) that covers
   the requested scopes.
3. An org policy `delegation_rules` names this agent (or all agents of a project) as allowed to
   act for users of the org, for the listed scopes. This policy is off by default and changing
   it emits `org.settings_changed`.

Otherwise the request fails with `access_denied` (our use of the code at the token endpoint;
RFC 8693 section 2.2.2 allows `invalid_request`, but `access_denied` is clearer and is listed in
the response for the client to handle).

**MACH-32.** The issued token's `act` claim is `{ "sub": <agent id>, "principal": "agent",
"agent_owner": <owner id> }`. If the subject token already had an `act`, it is nested inside the
new one, so the chain reads from the most recent actor outward ([RFC 8693] section 4.1). A chain
longer than 4 actors fails with `invalid_request`.

**MACH-33.** *Conservative choice:* impersonation, meaning a token whose `sub` is another
principal and that has no `act`, is not supported. Every token that one principal obtains for
another carries an `act` claim. There is no administrator "log in as user" feature.

**MACH-34.** The result never exceeds either party's rights. This server enforces the narrowing
rules of section 7.2 for scopes and audience. Resource-level rights are decided by Loams'
authorizer, which checks the subject and every actor in `act` ([15](15-loams-integration.md)
section 4).

### 7.4 Attenuation (vending)

**MACH-35.** A holder of an access token may exchange it, with no actor, for a narrower one for a
sandbox or a sub-task. The client must be the subject token's `client_id` or, for machine
principals, the principal itself. The result follows section 7.2 and may also be bound to an
agent session (section 7.5). Its `act` is the subject token's `act` unchanged.

**MACH-36.** The new family records its parent: its `origin` is `token_exchange` and its
`parent_family_id` names the subject token's family. No claim in the token names the parent.
Revoking the parent family revokes every
family vended from it (the fan-out worker follows the `parent_family_id` field of
`token_family.created`; [04](04-event-catalog.md) section 3.9 adds it for token exchange).

### 7.5 Lifetimes and agent sessions

**MACH-37.** Lifetimes of tokens whose `sub` or any `act` member is an agent:

- at most the agent's `token_ttl_cap` (default 15 minutes, never more than 1 hour);
- at most the subject token's remaining lifetime;
- at most the agent session's `expires_at` when bound.

**MACH-38.** An agent session ([03](03-data-model.md) section 2.12) is started with
`POST /api/v1/agent-sessions` ([17](17-management-api.md)) by the agent itself, by its owner, or
by a Loams supervisor with the right to vend for the agent. It has a purpose and an expiry of at
most 24 hours.

**MACH-39.** The extension parameter `agent_session=<id>` on a token exchange binds the issued
token to that session. The session must be active, belong to the agent that is the token's
`sub` or the outermost `act`, and be in the same org. The token carries the claim
`agent_session` with the session id. The issuing batch read-checks the session's stream, so
ending the session and issuing a token under it cannot both succeed (ES-10).

**MACH-40.** Ending an agent session (`agent_session.ended`) revokes every family bound to it
through the fan-out, and introspection reports their tokens inactive at once because it checks
the session's state (ES-11).

### 7.6 Agent-bound applications (the MCP flow)

An MCP client such as a coding assistant signs a user in with the authorization code flow and
PKCE, and then calls Loams on the user's behalf (Loams design 19 section 5.2, flow 2).

**MACH-41.** An application may be bound to one agent (application field `agent_user_id`, set at
creation, same org). Tokens it obtains through the authorization code flow have the user as
`sub` and carry `act: { "sub": <agent id>, "principal": "agent", "agent_owner": <owner id> }` and
`may_act: { "sub": <agent id> }`.

**MACH-42.** The consent screen for an agent-bound application names the agent, its owner, the
scopes and the audience, and says that the agent will act on the user's behalf. *Conservative
choice:* agent-bound applications are never `first_party`, so consent is always shown.

**MACH-43.** An agent-bound application may receive refresh tokens (users would otherwise sign in
every 15 minutes), with rotation and reuse detection as for any public client
([08](08-tokens.md)), but each access token's lifetime is capped by MACH-37.

### 7.7 Workload identity federation

An agent running in an environment that already gives it an OIDC token (a CI runner, a
Kubernetes service account, a cloud workload identity, a sandbox runtime) exchanges that token
for one of ours without holding any secret of ours (Loams design 19 section 5.2, flow 1).

**MACH-44.** A trust policy on an agent ([03](03-data-model.md) section 2.3) has:

| Field | Rules |
|---|---|
| `policy_id` | Server-assigned |
| `issuer` | Exact `https` issuer URL of the external provider |
| `audience` | The exact `aud` value the external token must carry. Default: this instance's issuer |
| `subject` | An exact string, or a pattern where `*` matches any run of characters other than `:` |
| `claims` | Optional map of claim name to exact string value, all of which must match |
| `max_token_age` | Default 10 minutes: the external token's `iat` must be no older than this |
| `allowed_scopes` | The most this policy can grant |

**MACH-45.** The request is a token exchange with `client_id=<agent id>` and no other client
authentication, `subject_token=<external JWT>` and `subject_token_type` of `jwt` or `id_token`.
The server:

1. Parses the JWT header without trusting it; refuses `none` and `HS*`.
2. Reads `iss` from the unverified payload only to select candidate trust policies of that
   agent with that exact issuer. No match fails with `invalid_grant` (the same error and timing
   as a signature failure).
3. Fetches the issuer's discovery document and JWKS through `HttpClient` (https only, outbound
   URL rules of [15](15-loams-integration.md) section 5.3), caches them for at most 1 hour, and
   verifies the signature with the key named by `kid`.
4. Checks `exp` (required, 60s skew), `iat` (required, within `max_token_age`), `nbf` if present,
   `aud` contains the policy's `audience`, `sub` matches the pattern, and every `claims` entry
   matches.
5. If the external token has a `jti`, records it in the replay cache until its `exp`; a repeat
   fails with `invalid_grant`.

**MACH-46.** The issued token has `sub` = the agent, `principal: agent`, `agent_owner`, scopes no
wider than the policy's `allowed_scopes` and the request, and the lifetime rules of MACH-37. The
token-family record stores the external `iss` and `sub` for audit (`federated_subject`).

## 8. Device authorization grant

[RFC 8628], for command-line tools and devices without a browser (for example `loams login` on a
headless machine).

**MACH-47.** Endpoint `POST /oauth/device_authorization`. The client must have the device-code
grant type. Public native clients authenticate with `client_id` only; confidential clients
authenticate as usual. The request may carry `scope` and `resource`.

**MACH-48.** The response:

| Field | Value |
|---|---|
| `device_code` | `lid_` + base64url of 32 random bytes; stored as SHA-256 |
| `user_code` | 8 characters from the 20-letter alphabet `BCDFGHJKLMNPQRSTVWXZ`, shown as `XXXX-XXXX` ([RFC 8628] section 6.1) |
| `verification_uri` | `<issuer>/device` |
| `verification_uri_complete` | `<issuer>/device?user_code=XXXX-XXXX` |
| `expires_in` | 600 |
| `interval` | 5 |

**MACH-49.** User codes are normalized before lookup: upper-cased, with hyphens and spaces
removed, and characters outside the alphabet rejected. A user code is unique among pending
device authorizations of the instance (the `user_codes` index); on a collision the server draws
again.

**MACH-50.** The `/device` page requires a signed-in session (it runs the normal login first). It
shows the client's name, the requested scopes and audience, and a warning to enter only a code
that the user obtained themselves on a device they control. The user must confirm explicitly;
`verification_uri_complete` pre-fills the code but never approves by itself.

**MACH-51.** Brute force: at most 5 wrong user codes per session per 10 minutes and 50 per
instance per minute (MetaStore counters), after which the page refuses entry for the rest of the
window. With 20⁸ ≈ 2.56 × 10¹⁰ possible codes and a 10-minute lifetime this keeps the chance of
guessing a live code negligible.

**MACH-52.** Polling the token endpoint with
`grant_type=urn:ietf:params:oauth:grant-type:device_code` returns, per [RFC 8628] section 3.5:
`authorization_pending` while pending; `slow_down` if the client polls sooner than `interval`
after its last poll, and the interval for that device code grows by 5 seconds; `access_denied`
after the user denies; `expired_token` after expiry. On approval the first successful poll
redeems the device authorization (`device_authorization.redeemed`) and creates a token family in
one batch ([05](05-event-store-and-projections.md) section 3.2). Later polls fail with
`invalid_grant`.

**MACH-53.** The resulting family is bound to the session that approved it unless the request
had `offline_access`, as for the code flow ([08](08-tokens.md)). Refresh tokens rotate as usual.

## 9. Revocation of machine principals

**MACH-54.** Deactivating or removing a machine user ends its agent sessions, revokes all its
token families and PATs (fan-out), and from the moment the user event is appended:
introspection of its tokens returns `active: false` (DM-14), and every token-issuing request
for it fails, because each issuing batch read-checks the user (ES-10).

**MACH-55.** Removing a machine key or a client secret takes effect on the next authentication.
Tokens already issued stay valid until they expire; an admin who wants them gone revokes the
user's families explicitly (`POST /api/v1/users/{id}/revoke-tokens`).

**MACH-56.** The `user.deactivated` and `user.removed` events are exported to identity-sync, so
Loams deletes the agent's or service account's tuples ([15](15-loams-integration.md) section 3).

## 10. Errors

| Situation | Error | HTTP |
|---|---|---|
| Bad or replayed client assertion, wrong secret | `invalid_client` | 401 |
| Bad or replayed JWT bearer assertion, unmatched trust policy, bad external token | `invalid_grant` | 400 |
| Grant type not enabled for the client or feature off | `unauthorized_client` | 400 |
| Scope not allowed or wider than the subject token | `invalid_scope` | 400 |
| Unknown or wider audience or resource | `invalid_target` | 400 |
| Delegation not allowed | `access_denied` | 400 |
| Malformed request, unsupported token type | `invalid_request` | 400 |
